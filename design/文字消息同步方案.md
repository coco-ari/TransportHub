# TransportHub 文字消息同步方案

> 本方案处于设计确认阶段。它复用现有 Syncthing，不新建聊天服务器，也不修改当前同步配置。

## 1. 想达到的体验

- 任意一台电脑在悬浮窗的统一时间线中输入文字、粘贴图片或投递文件。
- 本机立即显示自己的消息气泡。
- 其他在线电脑收到后，文字自动出现在同一个消息框中。
- 离线电脑重新上线后自动补齐历史消息。
- 支持中文、换行、网址、长文本、图片和文件卡；正文始终按纯文本显示，不执行 HTML 或脚本。
- 消息可显示“等待同步”“已送达 2/3 台”等状态，但“送达”不等于用户已经阅读。

所有需要显示消息的电脑都需要安装并运行 TransportHub 投递窗；只安装 Syncthing 的电脑仍会同步底层消息文件，但不会出现聊天界面。

## 2. 为什么不能共用一个聊天记录文件

不能让多台电脑同时追加同一个 `messages.json`、数据库或文本日志。两台电脑离线时分别修改它，恢复连接后 Syncthing 会得到两个不同版本并生成冲突副本，消息顺序和内容都很难可靠合并。

推荐使用“每条消息一个不可变文件”：

```text
%USERPROFILE%\TransportHub\
└─ .transporthub\
   ├─ messages\
   │  └─ <发送设备ID前缀>\
   │     └─ 2026-08\
   │        ├─ 01K2...A8.json
   │        └─ 01K2...Q3.json
   └─ receipts\
      └─ <消息ID>\
         ├─ <接收设备A>.json
         └─ <接收设备B>.json
```

每条消息使用全球唯一的 ULID/UUID 文件名。不同电脑永远创建不同文件，因此多机同时发送也不会互相覆盖。

## 3. 消息格式

建议第一版采用下面的 UTF-8 JSON 格式：

```json
{
  "schema": 1,
  "id": "01K2JQH9EJ9Y8R2H7RYXK8A6FM",
  "kind": "text",
  "senderDeviceId": "DEVICE-A-...",
  "senderName": "WORKSTATION-A",
  "createdUtc": "2026-08-12T15:45:12.284Z",
  "text": "今天的设计资料已经整理好，请大家查看。",
  "targetDeviceIds": ["DEVICE-B-...", "DEVICE-C-..."]
}
```

约束：

- `kind` 第一版允许 `text`、`link` 和 `attachment`。附件事件只保存受控相对路径、MIME、大小和哈希，不保存远端绝对路径。
- 单条文字最多 `32 KiB`；更长内容作为普通 `.txt` 文件投递。
- 文件总大小设置硬上限，未知字段可忽略，未知 `schema` 或 `kind` 不渲染。
- `targetDeviceIds` 保存发送当时的目标设备，用于稳定计算送达数量；之后新加入的电脑仍可看到历史，但不改变旧消息的分母。
- 消息创建后不再修改。编辑、撤回、表情等需要另建不可变事件，第一版不实现。

## 4. 发送和接收流程

### 发送

1. 用户按 `Enter` 或点击发送；`Shift + Enter` 用于换行。图片粘贴和拖拽文件会立即进入投递流程。
2. 程序生成消息 ID、UTC 时间和目标设备列表。
3. 先写临时文件，写入完成并刷新磁盘后再重命名为最终 `.json`。
4. 本机时间线立即显示气泡，状态为“等待同步”。
5. Syncthing 检测新文件并同步到其他电脑。

### 接收

1. 其他电脑的 Syncthing 把消息文件完整写入本地同步目录。
2. 投递窗通过文件系统监听发现变化，同时定期补扫，避免漏掉事件。
3. 校验路径、大小、JSON 结构和消息 ID；通过后作为纯文本加入时间线。
4. 接收端创建一个属于自己的不可变回执文件。
5. 回执通过 Syncthing 返回发送端，发送端更新为“已送达 2/3 台”。

Syncthing 本身使用文件系统监听和定期扫描检测变化，因此在线消息通常会较快出现，但设计上不承诺固定秒数。官方文档说明文件系统事件会先被批量处理，默认可能有约 10 秒检测延迟。

## 5. 回执的准确含义

回执文件表示：

- 消息文件已经到达该电脑；
- 该电脑的 TransportHub 已成功解析，并把消息加入本地时间线。

它不表示电脑使用者已经看过消息，因此界面使用“已送达”，不使用“已读”。

建议状态：

| 状态 | 含义 |
|---|---|
| 正在保存 | 本机消息文件尚未完整落盘 |
| 等待同步 | 本机已保存，尚未收到远端回执 |
| 已送达 2/3 台 | 3 台目标电脑中有 2 台投递窗已接收 |
| 已送达全部设备 | 发送时的所有目标电脑都已接收 |
| 等待离线设备 | 已知仍有目标电脑离线 |
| 同步服务离线 | Syncthing 未运行；服务恢复后继续 |

## 6. 时间线和本机索引

- 所有消息文件是唯一真实来源。
- 每台电脑可以在 `%LOCALAPPDATA%\TransportHub` 保存一个只属于本机的索引，加快启动和搜索。
- 本机索引绝不放入同步目录；损坏或删除后可以从消息文件重新生成。
- 时间线按 `createdUtc` 排序，时间相同再按消息 ID 排序。电脑系统时间严重不准时可能出现顺序偏差，因此应保持 Windows 自动校时开启。
- 默认先载入最近 200 条，向上滚动再分页读取，避免一次加载全部历史。

## 7. 安全处理

- 消息正文始终按纯文本转义显示，不能直接渲染 HTML、JavaScript 或远端提供的富文本。
- 只接受 `http://` 和 `https://` 网址卡，不支持自定义可执行协议；第一版只同步网址文本，不自动下载远程图片。
- 不接受消息中的任意本机绝对路径。
- 只有已经获得 `transporthub-data` 共享权限的设备才能获得消息文件；丢失电脑后应从 Syncthing 设备列表移除。
- 删除消息文件会像普通同步删除一样传播。第一版不提供全局删除；“从界面隐藏”只修改本机索引。

## 8. 界面方案

悬浮窗不再拆分“文件”和“消息”页面。文字气泡、图片缩略图和文件卡统一按时间排列；标题和状态压缩，时间线占据窗口主体：

```text
┌──────────────────────────────────┐
│ 全部电脑              3 在线/4台 │
├──────────────────────────────────┤
│ PC-OFFICE                        │
│ ┌──────────────────────────┐     │
│ │ 客户反馈已经汇总好了。    │     │
│ └──────────────────────────┘     │
│                                  │
│             ┌──────────────────┐ │
│             │ 资料我发过去了。 │ │
│             └──────────────────┘ │
│                   已送达 2/3 台 │
├──────────────────────────────────┤
│ 📎  输入消息……                 ➜ │
└──────────────────────────────────┘
```

消息框启动后自动显示已同步的历史，收到新消息时滚到最下方；用户正在查看旧消息时不强行跳动，只显示“有新消息”按钮。单击文字复制全文；单击文件或图片只在资源管理器中定位本机副本，不直接执行或打开文件内容。

## 9. 第一版不实现

- “已读”状态、正在输入提示。
- 修改、撤回、引用回复、表情和语音消息。
- 严格的服务器统一时序。
- 云端消息代存；离线补收依赖至少有一台持有完整数据的在线节点。
- 在没有安装 TransportHub 投递窗的电脑上显示消息气泡。
